# 性能の測定と最適化の記録

対象は Phase 14 で確定した 8 シナリオです。条件は PostgreSQL 16、資産 10 万件(restricted 5%)、ドメイン 50、Lineage 深さ 10 の分岐、Product 500、承認待ち 1,000 件です。SQLite は測定しません。

## 実行方法

```sh
export EDGF_DATABASE_URL=postgresql+psycopg://...
python scripts/perf/seed.py --reset          # 乱数のシードが固定なので、同じ引数なら同じデータになる
sh scripts/perf/serve.sh &                   # 127.0.0.1:8100、4 ワーカー
python scripts/perf/run.py --host http://127.0.0.1:8100 --output perf/results/now.json
python scripts/perf/compare.py perf/results/now.json
```

`compare.py` は `perf/baseline.json` より p95 が 30% 以上悪化する(監査の書き込みは件数が 30% 以上低下する)か、エラー率が 1% を超えると失敗します。目標の未達は表示だけで、失敗にはしません。

`run.py` に `--baseline perf/baseline.json` を渡すと、悪化したシナリオだけを最大 2 回まで再計測します。判定は 3 回のうち最も良い回で行います。エラーで速く返っただけの回は選びません。各回の結果は結果の JSON の `attempts` に、再計測したシナリオは `retried` に残り、CI では artifact と job summary で確認できます。

CI(`.github/workflows/perf.yml`)は手動と週次で動き、Pull Request ごとには動きません。100 万件のプロファイルは手動の入力 `profile=million` でだけ動きます。**100 万件は未検証です。**

## ディスクの詰まりの仮説の検証

**仮説**: 監査の書き込みが 141 件/秒に落ちた失敗(実行 `42576551616`、p95 300ms、p99 690ms)は、ディスクの書き込みの詰まりが、advisory lock で直列にした書き込みに波及したもの。

**方法**: 監査のシナリオの前後で `pg_stat_wal` と checkpoint の統計の差分を取り、`/proc/diskstats` と `/proc/stat` を記録しました。手動で 8 回起動しています。

PostgreSQL 16 には `pg_stat_checkpointer` がありません(17 から)。checkpoint の統計は `pg_stat_bgwriter` から読み、17 以降なら `pg_stat_checkpointer` から同じ項目で読みます。`track_wal_io_timing` は既定で off なので、CI の DB でだけ有効にしています。

| 実行 | ディスク | 件/秒 | p95 ms | p99 ms | WAL sync ms | 書き込み待ち ms | 最大 busy % | iowait % | 書き込み MB | checkpoint 完了 |
|---|---|---|---|---|---|---|---|---|---|---|
| `42580046080` | sda | 188 | 93 | 100 | 1,095 | 0.18 | 4.7 | 0.7 | 77 | 1 |
| `42580052958` | sda | 215 | 81 | 92 | 1,193 | 0.17 | 5.3 | 0.8 | 83 | 1 |
| `42580061114` | sda | 207 | 82 | 91 | 801 | 0.11 | 4.9 | 0.5 | 80 | 1 |
| `42580068551` | nvme | 301 | 59 | 79 | 1,164 | 0.47 | 9.9 | 0.8 | 109 | 0 |
| `42580075668` | sda | 206 | 84 | 97 | 1,078 | 0.16 | 6.2 | 0.7 | 81 | 1 |
| `42580880576` | nvme | 232 | 76 | 90 | 1,019 | 0.82 | 11.1 | 0.7 | 88 | 0 |
| **`42580887084`** | nvme | 225 | **110** | **410** | **5,886** | **2.30** | **65.6** | **5.1** | **199** | 0 |
| `42580893190` | sda | 198 | 87 | 99 | 1,071 | 0.16 | 4.2 | 0.6 | 79 | 1 |

CPU の steal は全回 0.0% でした。

**分かったこと**

- 8 回のうち 1 回(`42580887084`)で p99 が伸び、同時に WAL の sync 時間(約 5.6 倍)、書き込み待ち、busy、iowait、書き込み量がそろって増えました。遅延の裾とディスクの待ちが一緒に動く例です
- その回でも件数は 225 件/秒で、基準値を割っていません
- 残りの 7 回はディスクに余裕があります(最大 busy 12% 未満、iowait 1% 未満)。ランナーの種類による件数の差(188〜301 件/秒)は、ディスクの待ちでは説明できません

**結論**

- **141 件/秒の失敗の原因は未確認です。** 失敗した実行には統計がなく、同じ大きさの低下も再現していません
- **遅延の裾とディスクの待ちの相関は未確認です。** 例が 1 回だけで、相関と言える数がありません
- **checkpoint との相関は未確認です。** checkpoint が完了した回はすべて p99 が 100ms 以下で、裾が伸びた回には完了がありません。ただし統計は完了時にしか増えないので、実行中だった可能性は否定できません。その回の余分な書き込み(約 120MB)の出どころも分かっていません

今後の週次の実行でも同じ統計が残るので、例が増えたら更新します。

## 原因

SQL の遅さではなく、速い SQL を何千回も発行していたこと(N+1)が主な原因でした。

- `EXPLAIN ANALYZE` で個々の SQL は問題ありません。検索の一覧は `qualified_name` の索引で約 1ms、`lineage_edges` は `source`/`target` の索引で 200 ノード分を約 13ms です。
- 検索の残りの時間は `X-Total-Count` の `count(*)` が占めます(9 万 5 千行の Seq Scan で約 60ms)。挙動に関わるので変更せず、目標内のため索引も足していません。
- 監査の書き込みは、チェーンの先頭を同時に読んだ書き込みが UNIQUE 違反で再試行を繰り返していました。

## 判断の記録

### Lineage: `WITH RECURSIVE` にせず、段ごとの一括取得にする

`lineage.traverse` は 1 段ごとに `IN` でまとめて辺を取ります(500 件ごとに分割)。SQL の数は深さに比例します。

`WITH RECURSIVE` を採らなかった理由は次の 3 つです。

- 出力の順序(幅優先、同じ段では登録順)と循環の扱いを既存と完全に揃えるには、結局 Python 側で並べ直す必要があること
- SQLite と PostgreSQL の両方で同じ結果を保証しやすいこと
- 深さ 10 で目標を満たしており、これ以上の複雑さに見合わないこと

### `readable_clause` に索引を足さない

`sensitivity` の条件に合う行は全体の約 95% で、選択性がありません。Planner は索引を使わず、足しても書き込みの負担が増えるだけです。

名前を伏せる処理(`NameRedactor`)が名前ごとに問い合わせていたのは、`preload` で先にまとめて読むようにしました。

### inbox の集約方式

判断できる案件の絞り込み自体は SQL にしていません。「同じ人が 2 回判断できない」「Custodian は判断できない」などの規則は `approvals` の Python 側にあり、SQL に重複させると規則がずれる危険があるためです。

代わりに `decidable_pending` が承認待ちを 500 件ずつ読み、関連する行をまとめて読み込んでから既存の判定を通します。SQL の数は案件の数に比例しません。

### DATSIS: TTL キャッシュを持たない

`/mesh/products/overview` は、リクエストの間だけ有効なスナップショット(`mesh_datsis.load_snapshot`)を使います。一覧の処理が終わると破棄します。

時間で失効するキャッシュを採らなかったのは、無効化の条件が多く(品質の実行、Contract、ポート、例外、Bundle、資産の属性)、古い判定を返すと Product の公開可否という振る舞いが変わるためです。性能目標は TTL キャッシュなしで満たしています。

### 監査チェーン: PostgreSQL では advisory lock で直列化する

`audit.record` は `pg_advisory_xact_lock` でチェーンの更新をトランザクションの終わりまで直列化します。

- 再試行の連鎖がなくなり、142 件/秒が 279 件/秒になりました
- チェーンの性質上、書き込みは 1 本に並びます。**監査を記録するトランザクションの長さが、そのまま全体の書き込みの上限になります**
- UNIQUE 制約と再試行は残しています(SQLite と、ロック外の経路に対する最後の防御です)

### 検索: `pg_trgm` を入れず、`lower(...) LIKE` にする

`q` を指定した検索は、`X-Total-Count` のために全行に部分一致をかけます。件数の SQL が約 100ms、一覧の SQL が約 16ms です。

- `ILIKE` を `lower(列) LIKE lower(パターン)` に変えました。結果は同じで(大文字小文字、記号、タグの完全一致をテストで確認)、件数の SQL は単独で約 30% 速くなり、手元の p95 は 180ms から 150ms になりました
- 本来の解決策は `pg_trgm` の GIN 索引と、用語の条件(`OR id IN (...)`)を `UNION` に分ける書き換えです。**PostgreSQL の拡張という新しい依存になるので、Phase 14 では入れていません**
- `X-Total-Count` の概算や上限は、API の挙動が変わるので採りません

## 未検証・制約

- 参照環境での測定をしていません
- 検索は CI のランナーで目標に届いていません。影響分析、inbox、監査の書き込みも届かない回があります(上の表)

- 100 万件のプロファイルは用意しただけで、実行していません
- 測定は 20〜30 秒の短いもので、長時間の劣化(VACUUM の影響、テーブルの肥大)は見ていません
- 接続プールの枯渇、複数ノードでの動作は対象外です
