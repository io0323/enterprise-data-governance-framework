# ADR 0001: 自動で是正してよい範囲 (自律統治の基盤)

- 状態: 提案 (Committee の承認は、プレイブックを含む Policy Bundle の承認で行う。後述の「承認の方法」)
- 日付: 2026-11-13
- 関連: 設計書 §4 Data Ownership、§5 Continuous Data Quality、§12 Data Privacy、§16 Governance Process、§20 Level 5 Autonomous Governance
- 実装: Phase 19 (`edgf/services/autonomy*.py`、`policies/remediation/playbooks.yaml`)

この ADR は、以降の実装の正とする。ADR と実装が食い違ったら、ADR を正として実装を直す。

## 1. 背景

§20 の Level 5 (Autonomous Governance) は「品質検知・分類・是正の大部分が自動化。統治が自己改善」を求める。
一方で、§4 Business Ownership は、データ資産の判断 (品質基準・アクセス・分類・利用可否) を業務部門の Owner に置き、
技術的な管理者 (Custodian) に承認の権限を与えないことを中核の原則にしている (`edgf/authz.py` はロード時に検証している)。

自動化の主体は、技術的な仕組みである点で Custodian と同じ立場にある。自動化の範囲を決めずに「是正」を任せると、
業務の判断が仕組みの側に移り、Owner の責任が名目だけになる (§4.3 のアンチパターン「Custodian への責任転嫁」)。
この ADR は、その緊張関係を次のように解く。

- 自動化の主体は、承認 (✓) の権限を一切持たない。業務の判断を含む変更は、提案を作るところまでで止める。
- 自動で実行してよいのは、権限や信頼を「下げる」方向で、元に戻せて、業務の判断を含まない操作に限る。
- 自動で実行した操作は、すべて監査に残り、Owner と Committee が取り消せる。取り消しが多い自動化は自動で止まる。

## 2. 自動化の主体

- 実行の主体は `system:autonomy` とし、プレイブックごとに `system:autonomy:<プレイブックの id>` とする。監査の actor はこの主体で記録する。
- この主体のロール `autonomy` は、IdP や開発用のヘッダからは得られない (認証で受け付けるロールの一覧に含めない)。
- 権限表 (`authz.PERMISSIONS`) と承認者のルールで、承認 (✓) の権限にこのロールを含める定義は、ロード時にエラーにする
  (Custodian に承認の権限を与えない検証と同じ仕組み)。
- 承認エンジンは、`system:autonomy` で始まる主体の判断を 403 で拒否する (権限表の外からの経路も塞ぐ)。

## 3. 自動化の 3 区分

| 区分 | 定義 | 実行 | 例 |
|---|---|---|---|
| A | 権限や信頼を下げる方向で、元に戻せて、業務の判断を含まない操作 | 自動で実行してよい | 品質の異常を検知した Certified の資産を draft に戻す / 条件が解消した品質の Issue を閉じる / 期限切れや対象の資産が無くなった閲覧の承認を取り消す / Issue を起票する |
| B | 業務の判断を含む、または権限や信頼を上げる方向の操作 | 提案だけを作り、人が承認する | 分類 (pii、pii_category、sensitivity、cde) の変更 / Owner の割当 / Policy の見直し |
| C | 取り返しがつかない、または統治そのものを変える操作 | 禁止 (カタログに存在させない) | 資産の削除、Legal Hold の解除、閲覧の承認の付与、承認の判断、Policy の公開、分類を下げる変更、データ本体への操作 |

- 区分 A の操作は、Issue の起票を除き、取り消せるように作る。取り消しは「操作の前の状態」に戻すことで行う。
- 判断に迷う操作は区分 B として扱う。区分を上げる (B → A) ときは、この ADR を改訂する。
- 操作は、コードに実装したカタログからだけ選べる。プレイブック (YAML) で区分 C の操作を書いたり、
  カタログの区分と異なる区分を書いたりした場合は、ロード時にエラーにする。
- 分類の提案は、保護を強める方向 (pii を立てる、sensitivity を上げる、cde を立てる) だけを作る。弱める方向は人が判断する。

## 4. 安全装置

1. 1 回の実行あたりの件数の上限 (プレイブックごと)。超えた分は実行せず、Issue を起票して人に知らせる。
2. 全体の停止スイッチ。`POST /autonomy/stop` は Committee と admin がすぐに実行できる (安全側の操作なので ✓ は不要)。
   再開の `POST /autonomy/resume` は Committee の承認 (✓。UI ではステップアップ) を必要とする。
3. プレイブックごとの自動停止。直近 30 日の「誤って実行した率」(取り消された件数 ÷ 実行した件数) が閾値を超えたら、
   そのプレイブックを止めて Committee に Issue を起票する。再開は 2 と同じく Committee の承認による。
4. 環境変数 `EDGF_AUTONOMY_ENABLED` (既定 false) が false なら、dry_run も含めて何も実行しない (記録も作らない)。
5. 区分 A の操作は、プレイブックで定めた日数のあいだ、対象資産の Owner と Committee が取り消せる。取り消しも監査に残す。
6. 実行の記録 (RemediationRun) に、操作の前後の状態と、根拠 (検知の値など) を残す。

## 5. dry-run から始める方針

- プレイブックには `mode` (dry_run / active) を持たせる。初期のプレイブックはすべて dry_run にする。
- dry_run では状態を一切変えず、「行うはずだった操作」と、その前後の状態だけを記録する。
- active への切り替えは、プレイブックの `mode` を変える Policy 変更として、Committee の承認と公開を経て行う。
  切り替えの判断には、dry_run の記録 (件数、対象、予想される前後の状態) を使う。

## 6. Committee の承認の方法

- プレイブック (`policies/remediation/playbooks.yaml`) と分類の規則 (`policies/classification/rules.yaml`) は Policy Bundle に含める。
  変更は既存の Policy 変更の承認 (`policy_change`、Committee ✓) と公開 (`policy.publish`) を経て有効になる。
- この ADR の承認は、初期のプレイブックを含む Policy Bundle の承認をもって行う。
  承認されて公開されるまで、active の Bundle にプレイブックは無く、自動の是正は動かない。
- 既存の環境では、ディスクのプレイブックを `POST /policies/reload` で提案し、承認と公開を経て有効にする。

## 7. 検知と提案の根拠

- 品質の異常の検知は、品質検査の実行履歴 (スコア、ディメンション別のスコア、件数) と、実行の間隔だけを使う。データの値は使わない。
- 分類の提案は、メタデータ (カラム名、説明文、Lineage の DIRECT の経路、Glossary の用語との紐付け) だけを根拠にする。
  ML のモデルや外部の LLM は使わない。データの値も見ない。
- どちらも、根拠 (使った値、中央値、MAD、傾き、一致した規則など) を結果に残し、説明できるようにする。

## 8. 見直しの条件

次のいずれかに当てはまったら、この ADR を見直す。

- いずれかのプレイブックが自動停止した (誤って実行した率が閾値を超えた)。
- 区分 B の提案の受け入れ率が高い状態が続き、区分 A へ移す提案が出た (移すときは、取り消せることと業務の判断を含まないことを改めて確かめる)。
- 新しい操作をカタログに加える。
- 規制や組織の変更で、§4 の役割の定義が変わった。
- 前回の見直しから 1 年が過ぎた (§16 Policy の年次見直しに合わせる)。

## 9. 結果

- 良い点: 自動化の範囲が宣言的で、承認の証跡が Policy Bundle の版として残る。誤った自動化は取り消せ、多ければ自動で止まる。
- 悪い点: 区分 B の提案は人の判断を待つため、自動化の効果 (自動是正率) は区分 A の範囲に限られる。
- 制約: 異常の検知は季節性や外部の要因を扱わない。分類の提案は辞書規則の網羅性に依存する。
